# Offline edits through an outbox

Supersedes [0005](0005-online-only-edits.md): every edit of a collection's content works offline. That covers checklists, notes, the day plan (put on a day, move, reorder, remove, day name and notes), places, stays and connections (create, edit, delete, duplicate a place, add one from the library), visits, "visited today", ratings, trails, activities (with their GPX file), photos and file attachments (add, rename, delete, cover), and the collection's own settings (name, dates, description, link, cover). Only what involves other people's accounts or a lookup on the internet still needs a connection: sharing and invites, archiving, creating or importing a collection, the generated day plan, and searching the web, Wikipedia or nearby places for something to add.

Each such edit is saved on the phone as an _operation_ ("tick Passports", "add a visit on 20.12.", "rate 4"), not a snapshot, in an outbox in SQLite next to the offline copy (`src/data/outbox/`, its own key, never cleared by an app update). Screens show the collection with the waiting operations laid over it, so the edit is visible at once, online or not. The outbox is sent in order at start, when the connection returns, when the app comes to the foreground and right after each edit; online, an edit goes out at once like before. Before sending, the collection is read again (the single request of [0001](0001-one-request-per-collection.md)) and the operation is replayed on what the server has now:

- **Checklists:** the change is applied to the current list, matching items by id and else by name (the server re-creates item ids on every save). Two people ticking different items no longer overwrite each other.
- **Notes:** AdventureLog has no versioning, but notes carry `updated_at`. An edit remembers the version it started from; when the server's differs at send time, the offline text is saved as a copy ("Packing (offline)") next to the other person's, and the user is told. Nothing is overwritten and nothing is lost. Several offline edits of one note are folded into one first.
- **"Visited today":** skipped when the place already has a visit that day. **Ratings:** last one wins.
- **Stays, connections, places and day names:** only the fields that were changed are queued, each with the value it had. At send time a field goes to the server only if nobody changed it meanwhile; a field both sides changed keeps the other person's value and the user is told ("someone else changed the same details"). The rest of the edit is saved.
- **Day plan:** a reorder applies our order to the entries we knew and keeps entries someone else added at the end; moving or removing an entry that is already gone does nothing.
- **Deleting** something already deleted does nothing. Deleting something created offline cancels its creation and everything waiting for it; taking an entry off a day it was only put on offline cancels both.
- **Visits, trails, activities, attachment names and the collection's settings** follow the same field rule as stays. Something added inside an object created offline (an activity on a new visit, a photo on a new place) follows it to its server id; a photo added offline can become the cover.
- **Adding a place from the library** reads the place again before sending, so the other collections it belongs to are kept.
- **Photos** are copied into the app's documents (the picker's copy lives in a cache the system may empty), shown from there at once, uploaded later and then moved into the offline cache under their server URL.
- **Created offline** (a note or checklist, also put on a day): it gets a temporary id; once created, later operations are pointed at the server's id, and a retry first looks for the object so a lost answer doesn't create it twice.

No answer (no connection, server error) leaves the operation waiting; an answer that refuses it (no permission, object deleted) drops it with an alert. The status row of a collection says how many edits are waiting. Signing out discards waiting edits, after a warning, because they belong to that account and server.

The cost: one more write path, a short window in which the server and the phone disagree, and conflicts resolved by keeping the other person's field or a copy of a note rather than merging text. Every new kind of edit needs its own entry, with its replay and conflict rule, in `src/data/outbox/kinds.ts` before it can be made offline.

**Considered: TanStack DB with `@tanstack/offline-transactions`** (checked 07.11.2026: `@tanstack/db` 1.0.0-rc.1.4, offline-transactions 1.2.0 with a React Native entry). It would provide the generic part: a durable FIFO outbox, retry with backoff, permanent-failure handling and connectivity/foreground triggers. It does not provide what makes this reliable against AdventureLog: replaying on the server's current state, field-wise conflicts, the note copy, folding and cancelling queued edits, or mapping server-generated ids onto later edits (it assumes client-generated ids and a server that honours idempotency keys; AdventureLog has neither). Adopting it would also mean moving the read path from the one cached collection response ([0001](0001-one-request-per-collection.md)) into normalised TanStack DB collections, a release-candidate dependency, and `@react-native-community/netinfo` (a native module: new builds) next to the `expo-network` the app already uses. The generic part here is about 180 lines (`src/data/outbox/queue.ts`); the domain rules (`kinds.ts`) would be needed either way. Revisit once TanStack DB 1.0 is stable, if the app moves to normalised local collections for other reasons.

Pending edits are shown everywhere the collection is: screens, and also widgets, reminders and the Live Activity ([0015](0015-glances-from-the-offline-copy.md)), so a departure changed offline is the one on the lock screen. Photos and files kept for upload are files on the phone and are never downloaded by the offline sync. Writes that need the server now (sharing, invites, archive, world marks, lookups) go through one online write path instead (`src/data/onlineWrite.ts`).

Checked on 08.11.2026 against the owner's server with `src/__e2e__/offlineSync.e2e.test.ts` (opt-in: `E2E_SERVER=<url> E2E_KEY_FILE=<file with an API key> npx jest src/__e2e__`; it creates a throwaway collection and deletes it again). Edits were queued without sending, the same things were changed through the API as "the website", then the real outbox synced: both checklist ticks kept, the note kept as a copy, the lodging's check-in kept from the website while the offline booking number went through, a location created offline arrived with its visit, rating and itinerary item, the day name, the reorder (with an item someone else added kept at the end), the move to another day, the collection rename, a trail and a deletion all arrived, and an object created and deleted offline never reached the server. The app's live path (checklist ticks, the "Als Nächstes" card) was checked on the iOS simulator; a real phone without signal is still to do.
