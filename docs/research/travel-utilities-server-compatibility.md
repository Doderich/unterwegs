# Travel utilities: AdventureLog server compatibility

Research checked **09.11.2026** against official AdventureLog docs and source. Baselines: [v0.13.1, `a890a170`](https://github.com/seanmorley15/AdventureLog/tree/a890a17001e7a9cd6b82916804acdc4070008f72) and current `main` fetched for this check, [commit `f92621f0` (03.11.2026)](https://github.com/seanmorley15/AdventureLog/tree/f92621f07b978765fc1284dc29af0b5e744ae930). Source review only; no deployment or live extension test. No existing research directory/convention was found, so this note starts `docs/research/`.

## Verified findings

- **No supported general plugin/extension mechanism was found** in either baseline. This is a bounded source-review conclusion, not a maintainer guarantee: documentation and backend searches found no plugin SDK, extension registration/configuration, or general outbound change-webhook interface. Django apps and URL routes are explicitly listed in [v0.13.1 settings](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/backend/server/main/settings.py) and [URLs](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/backend/server/main/urls.py), as they are in [current settings](https://github.com/seanmorley15/AdventureLog/blob/f92621f07b978765fc1284dc29af0b5e744ae930/backend/server/main/settings.py) and [URLs](https://github.com/seanmorley15/AdventureLog/blob/f92621f07b978765fc1284dc29af0b5e744ae930/backend/server/main/urls.py). Installing a custom Django app would therefore require a custom server configuration/image; Django's extensibility alone does not make it an AdventureLog-supported plugin.
- **“Integrations” are built-in implementations, not third-party plugins.** Immich, Strava, Wanderer and Endurain are explicitly registered in the [v0.13.1 integration router](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/backend/server/integrations/urls.py); that router is unchanged in [current main](https://github.com/seanmorley15/AdventureLog/blob/f92621f07b978765fc1284dc29af0b5e744ae930/backend/server/integrations/urls.py). The Stripe webhook is a billing-specific inbound endpoint, not a collection-change subscription mechanism ([billing routes](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/backend/server/billing/urls.py)).
- **The REST API is an explicitly documented integration boundary.** Official [API-key documentation](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/documentation/docs/configuration/api_keys.md) describes scripts/integrations, separate revocable keys and `X-API-Key` or `Authorization: Api-Key`. The [authenticator](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/backend/server/users/authentication.py) authenticates as the key's user. The [key model](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/backend/server/users/models.py) has no read-only or feature-specific scopes; a separate key provides independent revocation, not narrower permissions. The API-key docs/authenticator and [resource routes](https://github.com/seanmorley15/AdventureLog/blob/v0.13.1/backend/server/adventures/urls.py) are unchanged in the checked current main.
- **Upstream contribution is the documented route for new server behavior.** Current [CONTRIBUTING.md](https://github.com/seanmorley15/AdventureLog/blob/f92621f07b978765fc1284dc29af0b5e744ae930/CONTRIBUTING.md) asks for an issue for features/behavior changes and PRs against `development`; feature merge waits for a linked issue labeled `ready` or `in progress`. Acceptance and release timing remain maintainer decisions.

## Architectural proposals for Unterwegs (not upstream capabilities)

**Prefer an optional companion service for app-specific utilities.** Give it its own API, storage and migrations; reference AdventureLog objects by server identity plus object UUID. Keep derived utility data there. Read AdventureLog through its authenticated HTTP API and write supported AdventureLog objects through that API only. Do not mount, query or modify AdventureLog's database, add tables to it, or patch its container. This keeps stock upstream deployable without the companion and avoids coupling to internal schema/migrations.

Make companion configuration explicit and capability-based (for example, its own versioned capabilities response); absence or failure disables only its utilities. Preserve ordinary stock-server login, collection reading, offline copies and edits. Prefer sending the companion only the inputs it needs. Background server-side reads require separately provisioned credentials and per-user authorization; never forward the mobile key automatically to another host. Without a verified change-feed mechanism, use on-demand refresh or conservative polling and reconcile permissions/deletions; immediate synchronization is not established.

**Contribute upstream when a feature belongs in the shared travel model or needs authoritative server permissions/events.** Propose small additive API/model changes through the documented issue/PR route. Until released and verified, expose those features only behind capability checks; keep the v0.13.1 path working. A private fork/custom Django app is possible engineering, but creates an additional server distribution to maintain.

These proposals follow the local [pinned-version decision](../adr/0011-pinned-server-version.md), [server facts](../SERVER.md) and [roadmap](../ROADMAP.md): the pinned deployment's API baseline is v0.13.1, other installations differ, and collection reads still come from `GET /api/collections/{id}`. The companion is an option to discuss, not an adopted ADR or a claim of upstream endorsement.
