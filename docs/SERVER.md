## Request rules

- The public domain routes `/api`, `/auth`, `/media`, `/accounts` through SvelteKit to Django. `/docs/` (Swagger) is **not** routed.
- `/api/x/` → **308** → `/api/x`. Call paths **without** a trailing slash.
- Auth header: `X-API-Key: al_…` or `Authorization: Api-Key al_…`. Both pass through the proxy.
- "Not logged in" responses come in two forms: **401** `{"detail":"Authentication credentials were not provided."}` and **400** `{"error":"User is not authenticated"}`. Treat both as logged out.
- `/media/…` (images, attachments) → **403 without the key**, 200 with `X-API-Key`. No thumbnail sizes; images are webp, ~270 KB each.

Headless allauth (checked 02.11.2026, no auth needed): `GET /auth/browser/v1/config` → login by `username_email`, MFA `totp` + `recovery_codes`, social provider `authentik` (`provider_redirect`), signup closed. `GET /auth/app/v1/config` → same, but **no social providers**. `/_allauth/…` is not routed.

Login for the app (`src/auth/serverLogin.ts`):

- `GET /auth/social-providers` → `[{name, url, usage_required}]`. On this server `usage_required: true` (`FORCE_SOCIALACCOUNT_LOGIN`): **password logins are rejected**, only SSO. `SOCIALACCOUNT_LOGIN_ON_GET` is on, so the provider `url` can be opened directly.
- Password (other servers): `POST /auth/app/v1/auth/login {username, password}` → 200 `meta.session_token`, or 401 with a pending `mfa_authenticate` flow → `POST /auth/app/v1/auth/2fa/authenticate {code}` with `X-Session-Token`. Wrong password: 400 `errors[0].code = "username_password_mismatch"`.
- allauth 0.63: the app `session_token` **is** the Django session key. The SvelteKit proxy forwards a `sessionid` cookie and adds CSRF, so `POST /auth/api-keys` with `Cookie: sessionid=<token>` returns the new key once (`key`). Invalid session → 401. `/csrf/` is not routed.
- SSO, preferred: system browser sheet (`src/auth/browserLogin.ts`, passkeys work) on `<provider url>?next=/unterwegs/login.html?state=…&name=…`. allauth 0.63.6 keeps a same-host `next` through the provider redirect (`ALLOWED_HOSTS=['*']`, only `http(s)` allowed). The page (`server/unterwegs-login.html`, served by the owner's server) creates the key and returns `unterwegs://login?key=…&state=…`. The app uses it only if `GET /unterwegs/login.html` contains `unterwegs-login-v1`.
- SSO, fallback: incognito WebView on the provider URL; once back on the website, injected JS calls `POST /auth/api-keys` same-origin and posts the key to the app. Passkeys don't work there (the app isn't associated with the identity provider's domain).

A key has no tie to how its user logged in: Authentik is only used on the website to get the session that creates the key.

Read-only authentication comparison on 04.11.2026, using the same valid API key: `/auth/user-metadata` returned 200; `/auth/browser/v1/account/email`, `/auth/app/v1/account/email` and `/auth/browser/v1/account/authenticators` returned 401 with `is_authenticated: false`. The key authenticates the user to DRF endpoints, whose configured authenticator accepts it. These allauth endpoints use their own session/token flow. SSO succeeds before key issuance, but the app stores the resulting key rather than retaining that session. This does not make all account/admin endpoints session-only.

## Account administration

Checked 04.11.2026 against the live API and pinned v0.13.1 source (`users/views.py`, `users/serializers.py`, website settings):

- `GET /auth/user-metadata` includes `public_profile`, `is_staff`, `has_password`, `disable_password`, `measurement_system`, `default_currency`, `date_format`, names and username (email is omitted).
- `PATCH /auth/update-user` accepts partial profile/preferences updates with the API key; an empty PATCH returned 200 without changing the account. Omit unchanged usernames. **Setting `public_profile: false` removes memberships of other people's shared collections and pending invites**, so the app confirms first and refetches collections/invites.
- `GET/POST /auth/api-keys` and `DELETE /auth/api-keys/{id}` work with the API key. A throwaway key was created and revoked successfully. Only the create response includes the raw `key`; the app keeps it in screen state and excludes the key list from the persisted query cache.
- `POST /auth/delete-account {confirmation, password}`: source-verified only, never exercised against the real account. `confirmation` must equal the username. A password is required only when the account has a usable, enabled one (`DeleteAccountSerializer`); accounts without one (SSO only) confirm with the username alone. Staff cannot self-delete (403). Success is 204.
- `GET /api/backup/export` produces an account ZIP; `POST /api/backup/import` restores one (source/schema verified, not exercised in the account checks). These are DRF API endpoints, distinct from collection exports. The app currently exports natively and links to website restoration; a native restoration UI is still missing.
- The server settings tabs are `/settings?tab=security`, `emails`, `data`, `admin`. MFA/password and email depend on the browser's allauth session; the app opens these in the system browser without sending its API key in the URL. Staff administration currently uses a website link; its endpoint/authentication coverage has not been audited for native management.

### Uploads, objects, deletes (verified 03.11.2026 on a throwaway collection, all removed; spikes S5–S9)

The SvelteKit proxy rejects form content types (`multipart/form-data`, `x-www-form-urlencoded`, `text/plain`, **and a missing `Content-Type`**) on POST / PATCH / DELETE unless `Origin` is the server's own origin: **403 `{"message":"Cross-site POST form submissions are forbidden"}`**. JSON requests pass with any or no `Origin`. So: every write sends `Content-Type: application/json` (also body-less DELETEs and `toggle_primary`), and uploads send `Origin: <server URL>`.

### Two-account collaboration checks (05.11.2026)

Live checks with two distinct accounts verified invite → revoke, invite → decline, invite → accept, duplicate-invite rejection (400), collaborator reads/creation/edits, and owner removal. A pending or revoked invite grants no private collection access. Removal revokes reads and writes to the owner's note and unlinks the removed collaborator's own location without deleting that location. Collaborators cannot rename, publish or delete the collection (404 on this live server). These are API checks; the native interaction remains unverified.

**Collaborator update requirement:** PATCH of notes, checklists, lodging and transportation must include the existing `collection` ID. Omitting it returns 403 (`You cannot remove the collection as you are not the owner.`), even for an edit to content alone. Including it passed live for all four object types; `client.edit` requires the field and `useCollectionEdits` supplies it. Checklist updates still require the full item list.

**Leave is blocked on the pinned server:** an accepted collaborator's `POST /api/collections/{id}/leave` returns 403 (`You do not have permission to perform this action.`). In v0.13.1, `CollectionShared.has_object_permission` denies non-owner writes to a Collection before the leave handler can remove the membership. Owner removal works as an alternative; the intended leave cleanup is not live-verified. This requires a server fix, not a different app payload.

Public collection checks verified anonymous and authenticated non-member reads, rejected non-member collection/note edits, and public/private propagation to the sample's locations, notes and lodging. The collection was restored to private. The fictional “Unterwegs – Gemeinsam nach Kyoto” sample remains shared with the second account, whose public profile was enabled and retained with the owner's approval. It contains two locations, two notes, a lodging, a transportation and a checklist. Temporary removal/leave-test locations were deleted; no existing travel data was changed.

## Managing integrations

Verified 04.11.2026 with read-only live requests and the pinned v0.13.1 `integrations/views/` and `serializers.py` source:

- API-key requests to `GET /api/integrations` and `GET /api/integrations/immich` return 200. Wanderer and Endurain detail GETs return 404 when not configured. Management reads bypass persistent query storage. Immich's detail response includes its API key on this version: the app's response schema strips it and presents an empty replacement field.
- Immich: POST `/api/integrations/immich` creates; PUT `/api/integrations/immich/{id}` updates with partial fields (a missing key keeps the stored one); DELETE removes it. PUT is intentional: the pinned custom `update` implementation does not accept the extra keyword passed by DRF's default PATCH handler. Creation/update validate the remote connection before saving.
- Wanderer: POST `/api/integrations/wanderer`, PUT `/api/integrations/wanderer/{id}` with `server_url, api_key`; a blank/missing update key keeps the existing one. POST `/api/integrations/wanderer/disable` removes the connection. Keys are write-only in responses.
- Endurain: POST `/api/integrations/endurain/connect {server_url, username, password}` returns a connection (201) or `{mfa_required: true, mfa_token}` (202). POST `…/mfa {mfa_token, mfa_code}` finishes sign-in. A failed MFA attempt consumes the pending challenge: restart connection rather than retrying the same token. POST `…/disable` removes it; changing accounts requires disconnect/reconnect.
- Strava: GET `/api/integrations/strava/authorize` supplies `auth_url`; its callback is `/api/integrations/strava/callback`. The app adds random OAuth state, intercepts the matching same-server callback inside its provider WebView, and exchanges the code at that callback with its API key. The server replies with a settings redirect; the app verifies `strava.user` through GET `/api/integrations`. POST `…/strava/disable` disconnects. Client ID/secret must already be configured on the server (`strava.global`). The live server has none, so a real Strava authorization remains untested.
- Google Maps key and Strava client credentials are environment settings, with no API to edit them. The app exposes status/explanation only for these server settings.

Management writes were tested with mocked HTTP responses, not against existing integrations; no real connection was changed or disconnected.
